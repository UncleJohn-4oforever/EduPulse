# EduPulse 1.1 — Codex 开发需求与实施说明

> 文档版本：1.1 · 2026-10-14  
> 目标：实现一套校区局域网内运行的轻量级教学数据采集和分析系统。  
> 交付要求：**实现可运行的软件，而非只生成原型图**。优先保证统计正确、填写简单、数据安全、容易部署。

## 0. 给 Codex 的执行指令

你是本项目的全栈开发负责人。请先检查当前仓库，再确定实现方式：

1. 如果仓库已经有可运行工程，**优先复用其技术栈和组织方式**，不要无故覆盖既有文件。
2. 如果是空仓库，使用 **React + TypeScript + Vite + Tailwind CSS（前端）**、**Python FastAPI + SQLAlchemy + SQLite（后端）**、WebSocket（实时广播）。如采用其他方案，先在 README 说明理由。
3. 先完成最小可运行闭环：管理员登录 → 创建教师账号 / 初始化班级 → 教师登录并维护班级 → 管理员发起广播 → 教师确认 → 后台查看准确统计 → 导出。
4. 分阶段实现与测试，每阶段完成后运行测试/构建，记录结果。不得将假数据看板当作已完成的真实统计。
5. 不连接任何外部付费服务，不需要云服务器，初期部署在校区一台 Windows 电脑，其他电脑/手机通过同一局域网访问。
6. 不要要求教师每次重新填写。必须持久化并预填上次数据。
7. 请产出 README、配置样例、初始化管理员方式、数据库迁移/创建方式、启动脚本、测试和说明文档。
8. 如项目细节不足，采用本文默认定义并在 README 的“设计假设”列出，不得随意扩张第一版范围。

## 1. 业务目标

教学主管希望定期通过校区局域网向教师广播“请检查并确认教学数据”，教师核对并修改已有班级、学生信息，提交确认后，主管可以实时查看：

1. **每名教师班级满班情况**：一对一班级/课次数量，一对三满班率，一对六满班率，以及一对三和一对六合计的容量加权满班率。
2. **每名教师教学负荷**：每周有多少节课，按一对一/一对三/一对六拆分。
3. **所有学生的信息**：当前就读的科目、任课老师、对应班级、年级，教师对该生在该科目的程度标签与文字评价。
4. **广播填报进度**：已确认/未确认教师、确认时间。
5. **导出**：分析看板导出 PNG 图片，明细报表导出 XLSX。

### 不做（1.0 明确排除）

- 不设置“班级状态”“学生状态”（如暂停、退班）。
- 不做收费、缴费、课消、续费、家校沟通、考勤、自动排课、教学质量打分。
- 不做智能合班建议或 AI 评价。
- 不要求老师在每轮广播重新建班、重填学生。
- 不依赖企业微信/微信推送：仅保证**已打开网页且在线**的客户端能实时收到广播；离线教师下次登录可看到仍有效的待确认任务。

## 2. 角色与权限

### 2.1 管理员/教学主管

- 登录，查看全校区教师、班级、学生、报表。
- 在后台维护**教师名单**，根据姓名一键生成对应教师的独立登录凭据；可单个或批量生成强随机初始密码、复制/导出凭据供主管**私下逐人发送**。
- 创建/停用教师账号、重新生成密码、设置老师名称及所属校区。重置密码后旧密码立即失效。
- 管理必要的基础字典，如科目、年级、校区；支持创建初始数据。
- 创建广播采集任务（标题、开始时间、截止时间、目标校区/教师范围）。
- 查看谁已确认，谁尚未确认。
- 导出 PNG 看板和 XLSX 明细。
- 可对明显重复的学生进行人工合并（优先放在第二开发阶段，但数据库从一开始支持稳定 student_id）。

### 2.2 教师

- 只查看、创建和编辑自己所授班级及班级内学生的教学评价。
- 能搜索已有学生并把其加入自己班级；找不到时创建学生。
- 可以新增、编辑、移除自己班级中的学生记录；删除/移除必须弹出确认，避免误操作。
- 可以维护自己班级的每周上课时段。
- 查看当前广播并提交“本轮数据已核对”确认；**不要求本轮必须有改动**。
- 不得访问其他教师私有评价、整体主管分析或批量学生导出。

> 身份验证不能只靠姓名下拉框。至少用账号密码登录，后端检查权限；密码只以安全哈希保存。HTTP 接口与 WebSocket 均须校验登录身份。

### 2.3 教师名单发放密码与登录（1.1 新增，必须实现）

**核心体验：主管预先维护教师名单 → 系统按教师生成随机密码 → 主管将对应密码单独发送给老师 → 老师使用自己的身份和密码登录 → 只能看到和编辑自己的班级、学生和评价。**

**主管端「教师账号与密码」页面：**
1. 显示姓名、唯一登录账号（可自动生成，避免同名冲突）、所属校区、账号状态、最近登录时间；列表支持增加教师、批量导入名单、停用账号。
2. 每位教师有「生成初始密码 / 重置密码」按钮；支持勾选未分配密码的教师后批量生成。密码由**密码学安全随机数生成器**产生，建议至少 14 位，包含字母与数字（可使用避免混淆字符的安全字符集）；不得用姓名、工号、固定规则或 `Math.random()` 推导。
3. 主管按姓名查看本次刚生成的 **姓名 + 登录账号 + 一次性明文密码**；支持单独复制和批量导出 CSV/XLSX，供主管通过私聊分发。页面提醒凭据属于敏感信息，不建议在公共群里发送。
4. **密码仅在生成/重置成功当次短暂展示，关闭后不可再次查看原始密码**。数据库只存加盐的强密码哈希（建议 Argon2id；不存明文、可逆加密文本或 Excel 凭据副本）。如果主管丢失密码，只能重新生成；不要开发“查看原密码”。
5. 单独给每位教师生成的密码必须互不关联。批量生成时仅影响被选中的教师；已发放的密码不得因刷新教师名单而自动变化。密码重置应记录操作者和时间，旧会话全部失效。
6. 第一位教学主管的账号通过服务器初始化命令安全创建，不使用公开写死的默认密码。教师不能访问这一页面，也不能创建其他老师账号。

**教师登录页：**
1. 输入「教师姓名/登录账号」和「密码」；建议正式登录以唯一账号为准，姓名仅作友好提示。若出现同名教师，必须明确区分账号，不能依赖姓名做身份验证。
2. 成功后直接进入「我的班级」，页头显示当前教师姓名；自动加载且只能加载归属此登录账号的班级、时段、学生关联和教学评价。
3. 登录失败给出不泄露账号是否存在的统一提示；提供退出登录。第一版不做短信、邮箱找回；忘记密码时联系主管重置。
4. 教师可在未来版本自行改密码；如第一版实现「修改自己的密码」，必须校验当前密码并使旧会话失效。不要强制教师填写其他额外注册信息。

**后端强制安全边界：**
- 每个班级以 `teacher_id` 绑定稳定教师 ID，所有教师端接口从服务器会话获取当前 `teacher_id`，**绝不信任客户端传入 teacher_id 来决定可操作数据**。
- `GET /api/teacher/classes` 必须只返回本人班级；获取、修改、删除某个班级，以及更改其学生和评价，都必须验证该班级归属当前教师，否则返回 403/404。禁止通过篡改 URL 或请求体访问其他老师的数据。
- 学生跨科身份可复用，但教师只能查看为关联自己班级所需的最小学生基本信息；**其他教师的评价和学生全局报科统计只给主管看**。
- 使用安全的服务器端会话或带适当保护的 HttpOnly Cookie（生产局域网部署也应考虑 HTTPS、SameSite、CSRF 防护）；登陆限速/失败次数限制、密码哈希、会话过期与注销。WebSocket 连接也执行身份校验。
- 登录/重置/账号停用写入审计日志（不包含明文密码）。老师被停用后会话立即失效。
- 在多人共用的办公室电脑上，教师退出登录后不能通过浏览器后退看到之前账户的敏感信息；敏感页面设置适当缓存策略。

**重要交付取舍：** 这套登录方式是第一版的**必做功能**，并非后续增强；保持教师填报表单原样，不改变广播修改旧数据的工作流程。

## 3. 教师端页面（重点：保留用户确认过的表单交互）

### 3.1 页面布局

教师登录后到「我的班级」。页头展示当前有效广播任务、截止时间、上次确认时间与本次修改提示。

按班级显示可折叠卡片；也可点击“新增班级”。每个班级的编辑表单包括：

| 字段 | 类型 | 示例 | 约束 |
|---|---|---|---|
| 老师 | 自动关联登录教师 | 张老师 | 默认不可更改；管理员可调配 |
| 科目 | 下拉 | 数学 | 必填 |
| 年级 | 下拉 | 高一 | 必填 |
| 班级显示名称 | 文本 | 周三三档 | 必填；允许同名，不能充当唯一 ID |
| 班型/容量 | 下拉 | 一对一 / 一对三 / 一对六 | 必填，容量分别 1/3/6 |
| 上课时段 | 逐行添加 | 周三三档 | 至少一个，可添加多个时段 |
| 学生名单 | 搜索已有 + 新建 + 移除 | 学生1、学生2 | 数量不可超过容量，后台也验证 |
| 学生程度 | 单选标签 | A / B / C | 每个学生在每个班级有独立评价 |
| 文字评价 | 多行输入 | 基础薄弱，函数应用题困难 | 可选，长度限制（如 1000 字） |

**表单交互（必须实现）：**

- 初次打开班级卡片，就看到现有数据；修改科目、年级、班型、时段、学生和评价；班型支持一对一/一对三/一对六。
- 每个学生一张小卡片：姓名输入/选择、A/B/C 单选、备注文本框、移除按钮。
- “+ 添加学生”按钮（达到人数上限时禁用）。
- 自动显示“当前学生 X / 容量 Y，满班率 Z%”；但系统只保存真实的学生关联关系，不单独手填满班率。
- 保存班级更改后，显示成功或清晰的错误提示；刷新后数据依旧存在。
- 广播期间可以对所有班级进行调整，最后点“确认本轮数据”。未修改内容保留。
- 如果没有变更，提供“数据无变化，确认提交”。
- 有未保存修改时离开页面或提交整轮确认，应给予明确提示。
- 手机端和电脑端均易操作，避免过小控件。参照此前确认的界面：两列基础字段、独立学生卡片、A/B/C 标签、备注框、添加学生按钮、满班率汇总和底部确认按钮。

### 3.2 学生身份（非常重要）

同名不同学生可能存在；同一学生可能参加多个科目/班级。不可简单按姓名合并，也不可按表单中的“学生1/2/3”位置识别身份。

- `student.id` 必须是全局稳定、数据库生成的唯一 ID。
- 教师“添加学生”：先搜索已有档案（最少展示姓名、年级和用于区分的内部编号）；找不到可以新建。
- 允许老师直接输入“学生1”“学生2”等临时名称，作为真实学生档案的显示名称，但系统通过 ID 识别；同名时必须人工确认，不自动合并。
- 统计学生报科数时，对一个学生在多个班级中的同一科目 **去重**；跨科目计多个科目。
- 学生个人评价应该标明科目、班级、教师和更新时间。

## 4. 课次/负荷口径

“周三三档”这样的名称 **不是可用于计算课次的可靠结构化数据**。应将“班级名称”和“每周上课时段”区分存储。

定义 `weekly_slots`：每条记录 = 某班级每周固定的一次授课时段，字段包括 `weekday`（1~7）、`slot_label`（如“三档”，初期可使用自由文本），可选的 `start_time` 和 `end_time`。

计算规则：

- 单班每周课次数 = 该班级下有效的周固定时段条数。
- 教师每周总课次 = 其所有班级的周固定时段数之和。
- 一对一课次、一对三课次、一对六课次按所属班级类型分组求和。
- **有 4 个学生的一对六班，一周上 2 次，只计教师负荷 2 次，不计 8 次。**
- 第一版“负荷”指**每周固定排课课次数**，不是已实际上课数、课程分钟数或可排时间占比，不得标记成百分比“饱和度”。
- 如果需要之后增加真实饱和度，再加 `available_weekly_slots` 或可排课时段，公式为已排/可排；不在本版做。
- 不自动根据名称“周三三档”解析时段；新增/编辑班级时必须同时配置结构化周课时段。UI 可便捷地生成该显示名称。

## 5. 管理端页面

### 5.1 教师满班率总览

按教师显示，支持校区、学科、姓名过滤与排序：

- 一对一班级数和对应每周课次数（不要用一对一 100% 混入小班满班率）。
- 一对三：班级数、实际学生席位数、总可用席位数、满班率。
- 一对六：同上。
- 一对三 + 一对六：合计容量加权满班率。
- 一对三/一对六可用空位数量，便于后续排班。
- 点击老师可展开班级列表，展示每个班的容量、学生人数、名称和时段。

公式：

```
某班满班率 = 班级内学生数 / 班型容量 × 100%
老师一对三满班率 = 其全部一对三班在读席位总数 / (一对三班数量 × 3) × 100%
老师一对六满班率 = 其全部一对六班在读席位总数 / (一对六班数量 × 6) × 100%
老师小班综合满班率 = (一对三学生席位总数 + 一对六学生席位总数)
                    / (一对三班数量×3 + 一对六班数量×6) × 100%
空余席位数 = 总容量 - 已使用学生席位数
```

- 如果该老师没有对应班型，显示 `—` / `N/A`，**不要显示 0%**，因为没有班不代表零满班率。
- “席位数”按学生与班级的关联计数，同一学生同时就读两个班级，在两班中分别占用席位；这与“去重后的学生人数”不同，前台字段要说清楚。
- 多老师共同授课不在 1.0 处理，默认一个班仅对应一名主讲老师。

### 5.2 教师负荷总览

按教师显示：一对一周课次、一对三周课次、一对六周课次、总周课次、班级数。可按总周课次数降序；点教师展开每周时段明细。

### 5.3 学生列表

字段：学生编号、姓名、年级、当前科目数、当前科目列表、各科任课教师、所属班级。搜索姓名/编号，按校区/年级/科目/老师筛选；点击学生展开：

- 按科目 → 任课老师 → 班级展示学生评价（A/B/C、文字内容、最后更新日期）。
- 同一个学生同科目多个班，只算 1 个科目，评价可显示多条并标明归属。
- 一名学生跨校区登记时原则上沿用同一 `student.id`，但普通教师只看到其获授权班级内的信息。
- 教师评价为教学内部信息，仅向有权限的管理人员和对应教师展示。

### 5.4 广播与提交管理

管理员发起采集任务，目标是指定校区的教师或选定教师；任务包含标题、开始/截止时间、创建者。广播时：

- 已打开系统的教师端通过 WebSocket 即时看到醒目提示；页面也定期/登录时读取未完成任务，防掉线漏消息。
- 教师更新已有数据后，点击“确认本轮数据”；允许无修改直接确认。
- 每个教师每个任务最多一条当前确认记录，可再次确认并更新时间，保留相关操作日志。
- 管理端实时显示 `已确认数 / 目标教师总数`、名单及确认时间。
- 截止时间到后，页面标记“已截止”，默认不能再确认，允许管理员新建下一轮；不自动误报历史数据为已确认。
- 若截止时仍有人未提交，标记为未确认；历史数据仍保留，不能默认为 0。
- 老师修改基础班级数据与“本轮确认”是两个不同操作：修改不自动等同确认。

### 5.5 数据快照与导出

- 当前看板支持导出 **PNG**，带生成时间、校区范围、数据统计口径、当前广播任务及完成情况；不含全部学生个人文字评价。
- 管理报表支持导出 **XLSX**，至少三个 Sheet：教师满班率、教师周负荷、学生科目/教师/评价明细；可额外导出班级明细和填报完成清单。
- 导出的表头、百分比、数值类型符合 Excel 使用习惯；中文不乱码。
- 数据库应记录每轮广播的**固定统计快照**（汇总与必要明细，或可重建的版本化记录），防止事后编辑覆盖之前统计；用户可选择某轮历史广播导出当时的 PNG/XLSX。
- 快照不要求老师额外填写。对未确认教师的数据必须标注“未经本轮确认”，不假装是本期已核验数。

## 6. 推荐数据模型

可调整实体命名，但必须保持这些关系：

- `users`：id、username（唯一）、password_hash、role(admin/teacher)、display_name、campus_id、enabled、password_issued_at、password_changed_at、session_version、last_login_at、created_at。`password_hash` 不可逆；重置时递增 `session_version` 使旧会话失效。
- `campuses`：id、name。
- `subjects`：id、name。
- `students`：id、display_name、grade、campus_id、created_at、updated_at。
- `classes`：id、teacher_id、subject_id、grade、display_name、capacity_type(1/3/6)、campus_id、created_at、updated_at。
- `weekly_slots`：id、class_id、weekday、slot_label、start_time(nullable)、end_time(nullable)、created_at。
- `enrollments`：id、student_id、class_id、created_at；UNIQUE(student_id,class_id)。
- `student_evaluations`：id、enrollment_id(unique)、level(A/B/C)、note、updated_by、updated_at；评价随具体班级学生关系存储。
- `broadcasts`：id、title、campus_id / target scope、starts_at、deadline_at、created_by、created_at。
- `broadcast_targets`：broadcast_id、teacher_id；冻结本轮目标教师集合，避免后续新增教师改变分母。
- `broadcast_confirmations`：broadcast_id、teacher_id、confirmed_at；UNIQUE(broadcast_id,teacher_id)。
- `broadcast_snapshots`：id、broadcast_id、captured_at、snapshot_json / versioned detail；保证历史导出结果不随当前数据编辑漂移。
- `audit_logs`：id、actor_id、action、entity_type、entity_id、timestamp、metadata_json；记录重要新增、修改、移除行为，避免误改无法追溯。

数据库表关系需有外键约束；删除班级/学生默认使用限制或明确确认与有审计记录的逻辑删除策略，避免意外级联抹除历史；即便 1.0 没有“班级/学生状态”字段，也必须保障历史快照可追溯。日期时间统一存储为 UTC，界面按 Asia/Shanghai 显示。

**注意：** 当前报名科目数应由 `students → enrollments → classes → subjects` 实时聚合得出，不要存一个可能过期的 `subject_count` 冗余字段。

## 7. 后端接口建议

采用 REST JSON API，WebSocket 作为广播推送通道。名称可按工程风格调整：

- `POST /api/auth/login`、`GET /api/auth/me`、`POST /api/auth/logout`
- `GET /api/admin/teachers`、`POST /api/admin/teachers`（添加教师账号、查看教师名单）
- `POST /api/admin/teachers/import`（可选：批量导入名单）
- `POST /api/admin/teachers/{id}/issue-password`（生成或重置**一次性展示**的随机密码）
- `POST /api/admin/teachers/issue-passwords`（批量生成，仅针对选定 ID）
- `PATCH /api/admin/teachers/{id}`（更改姓名、校区、启用/停用）
- `POST /api/auth/change-password`（可选：教师修改本人密码）
- `GET /api/teacher/classes`、`POST /api/teacher/classes`
- `PATCH /api/teacher/classes/{id}`、`DELETE /api/teacher/classes/{id}`（删除必须明确授权和审计）
- `PUT /api/teacher/classes/{id}/weekly-slots`
- `GET /api/students/search?q=...`（教师搜索结果限最小必要信息）
- `POST /api/students`（教师可创建必要学生档案）
- `POST /api/classes/{id}/enrollments`、`DELETE /api/classes/{id}/enrollments/{enrollment_id}`
- `PUT /api/classes/{id}/enrollments/{enrollment_id}/evaluation`
- `GET /api/broadcasts/current`、`POST /api/broadcasts/{id}/confirm`
- `POST /api/admin/broadcasts`、`GET /api/admin/broadcasts/{id}/progress`
- `GET /api/admin/reports/occupancy`、`GET /api/admin/reports/workload`
- `GET /api/admin/reports/students`、`GET /api/admin/reports/export.xlsx`
- `GET /api/admin/reports/export.png`（也可以由前端可靠导出，确保内容与后端统计一致）
- `GET /api/admin/broadcasts/{id}/snapshot`
- `WS /ws/events`（完成身份认证，并按权限/校区推送事件）

要求后端统一计算统计，前端只显示；不能仅靠前端限制容量和越权访问。建议使用 Pydantic 做请求校验、数据库事务维护班级与学生关联。

## 9. 安全、可靠性、部署

- 只有授权管理员可查看全部教师负荷、所有学生评价和导出敏感数据。
- 所有写入必须进行服务端字段验证、对象权限检查、关联完整性检查。
- WebSocket 不信任客户端声明身份，采用与 REST 相同的会话鉴权。
- 密码存安全哈希；初始管理员密码通过首次初始化配置，不在仓库写死通用密码。
- 跨站请求保护、同源策略、安全 Cookie/会话策略按部署方式正确设置；不在日志记录明文密码及学生敏感评价。
- 局域网部署优先；不要直接将服务暴露在公网。若跨校区访问需要公网，则另行设计 HTTPS/VPN/访问控制。
- 提供 `start.bat` 或等效 Windows 启动方法，可一键启动前后端的生产构建版本；README 说明其他设备如何通过 `http://校区主机IP:端口` 访问。
- 数据持久化目录与程序代码分开；提供手动/定期备份 SQLite 的办法、恢复说明。备份时使用 SQLite 兼容备份方法，避免直接复制正在写入的数据库导致损坏。
- 对后台任务断线、刷新、重复提交、并发操作做合理处理。SQLite 开启外键及适用的 WAL 模式。
- 真实学生数据不得加入示例数据、测试、提交 GitHub 或日志；附 `.gitignore` 忽略数据库、备份、env、密钥、导出文件。

## 10. 验收案例（Codex 必须编写自动测试）

### 10.1 满班率

- 教师甲有 3 个一对三班，人数分别是 1/2/3；有 2 个一对六班，人数分别是 2/4。
- 一对三满班率应为 `(1+2+3)/(3*3) = 66.67%`。
- 一对六满班率应为 `(2+4)/(2*6) = 50%`。
- 小班综合满班率应为 `12/21 = 57.14%`，**不可简单平均 66.67% 与 50%**。
- 无一对六班时，该班型结果显示 N/A，不显示 0%。
- 一对一单独统计，不混进小班综合满班率。

### 10.2 教学负荷

- 同一一对六班 4 名学生，每周周三、周六各上 1 次：该班计 2 节/周，而不是 8 节。
- 同老师再有一个一对一班每周 1 次：总课次 3；其中一对六 2、一对一 1。
- 班级显示名称修改，不会改变周课次数。

### 10.3 学生去重与评价

- 学生 A 同时报数学、英语，两科老师分别填写：学生列表应该只有一个学生 A，显示 2 科、2 位任课老师及两条对应评价。
- 学生 A 同科目参加两个班：报科数仍是 1，不重复计为 2。
- 存在两个同名学生时不能自动合并。
- A/B/C 标签与文字评价修改后能保存、刷新可见；非授权教师不可读取。

### 10.3A 登录与教师数据隔离（新增强制验收）

- 主管建立「张老师」「李老师」两条教师记录，分别生成随机初始密码，复制姓名、唯一账号和对应密码给两位老师。
- 使用张老师的账号密码登录，进入的「我的班级」只显示张老师的内容；李老师亦然。
- 张老师尝试用浏览器 URL、API 请求参数或班级 ID 读取、修改、删除李老师的班级或评价：服务端拒绝。
- 主管查看教师名单可再次重置张老师的密码，**不能查看旧密码**；重置后旧密码无法登录、旧会话失效，李老师密码不受影响。
- 两位同名教师仍具有不同登录账号，互不能访问对方记录。
- 无登录的请求无法访问教师端数据；教师无法调用主管的生成密码、报表、导出接口。
- 刷新页面不导致教师密码变化；密码明文不出现在数据库、日志或持续显示的主管页面。
- 管理员停用账号后，该教师当前会话不能继续读写。

### 10.4 广播与确认

- 管理员发起面向 3 位老师的广播后，已在线教师端收到提示。
- 其中 2 人确认（允许零修改确认）：管理端显示 2/3；第三人显示未确认。
- 关闭浏览器的教师重新登录，在截止前仍能看到任务。
- 教师只保存修改、不点击确认，不能算作已确认。
- 过期任务不可普通提交。
- 广播目标名单在创建后冻结，后增加老师不改变该任务分母。

### 10.5 历史与导出

- 先完成广播 A 快照，再修改班级人数并完成广播 B；导出广播 A 时仍显示当时数据。
- XLSX 打开有正确中文表头、教师统计、负荷统计、学生评价明细。
- PNG 清晰可读，含统计时间及当前数据口径。
- 普通教师访问管理员报表/导出接口应被拒绝。

## 12. 最终完成标准

必须可以真实操作以下场景：

1. 管理员在教师名单创建张老师、李老师，为两人分别生成随机初始密码，通过私聊分发对应账号和密码。
2. 张老师使用自己收到的账号密码登录，只看到本人信息，建立“高一数学 · 周三三档 · 一对六”，添加 3 名学生，为每位选择 A/B/C 程度并填写备注；再配置本班周三三档时段。
3. 李老师添加一个英语班，并从已有学生中选取同一名学生，填写英语评价。
4. 管理员看到正确的满班率、教师每周课次数、学生多科任课教师及两科评价。
5. 管理员广播本周核对任务，两位老师调整或确认现有数据，无需重复建班。
6. 管理员实时看到两人确认，导出 PNG 和 XLSX。
7. 之后老师修改班级人数，新统计自动变化，但历史广播快照仍可按原数据导出。
8. 服务重启后用户、班级、学生、评价、历史记录全部仍在。

> 核心原则：**老师只维护实际班级与学生信息；系统自动计算统计；每轮广播只是对现有数据进行更新和确认。**
